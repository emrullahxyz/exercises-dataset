# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Two things share one repo:

1. **A static exercise dataset** — `data/exercises.json` (1,324+ records) plus one `.jpg` thumbnail (`images/`) and one `.gif` animation (`videos/`) per exercise. Each record carries 4-language instructions (en/es/it/tr). This is the published, reusable artifact (README.md documents it for outside consumers).
2. **Three standalone HTML apps** built on that data — no framework, no bundler, no `package.json`. Each is a single self-contained file opened directly in a browser or served statically.

There is **no build step**. What you edit is what ships. The old Python generators (`build_html.py`, `fix_html.py`, `refactor.py`, etc.) were deleted on purpose — do not resurrect them. `my_workout.html` is hand-edited and is the single source of truth for the workout app.

## Running locally

Serve the repo root over HTTP (relative media paths need a server, not `file://`):

```
python -m http.server 8734
```

The `.claude/launch.json` "static" config does exactly this. Then open `index.html`, `setup.html`, or `my_workout.html`. GitHub Pages serves this same repo in production, so relative paths (`images/...`, `videos/...`) work identically local and live.

## The three HTML apps

- **`index.html`** (~6 MB) — public exercise browser: search, filter, infinite-scroll grid, detail modal with GIF + multilingual instructions. Large because the dataset is inlined.
- **`setup.html`** — static developer guide (SQL `CREATE TABLE` + INSERT generation, client snippets in 7 languages, LLM-prompt builder). Pure reference content, no live backend.
- **`my_workout.html`** — the actively developed app: a personal 4-day workout tracker that persists set/kg/rep notes to a live backend. This is where nearly all real work happens.

## `my_workout.html` architecture

All logic is in one inline `<script>` (starts ~line 1222). Key pieces:

- **`EXERCISES_RAW`** — a trimmed copy of `data/exercises.json` (only fields the app uses: `instruction_steps` limited to `en`+`tr`; no `it`/`es`, no paragraph `instructions`, no `created_at`). Indexed into `BY_NAME` by exercise name.
- **`PLAN`** — the 4-day split: `upperA` (Mon), `lowerA` (Tue), `upperB` (Thu), `lowerB` (Sat). Posture/mobility work is embedded as warm-up and finisher blocks, not a separate day. Per-exercise optional flags: `section` (full-width heading before the card), `posture` (🦴 badge), `warmup` (shows 🦴 instead of a number, excluded from main numbering), `cycle` (every-other-week badge, excluded from weekly set counts).
- **Notes persistence** — talks to `API_URL = "https://emrullah.xyz/api/workout/notes/"`:
  - `fetchNotes(exercise_id, setsString)` on modal open — has race-condition guarding (`if (currentExerciseId !== exercise_id) return;` so a stale response for a previously-opened exercise is discarded).
  - `scheduleSave()` — 1000 ms debounced `POST` (upsert) on any input change.
  - Set rows are generated by `parseInt`-ing the `PLAN` set string (`"3×10–12"`, `"3×60sn"` → 3 rows).
- **Auto-expanding inputs (do not break):** number inputs have no fixed width — JS sets inline `width: ${text.length + 0.5}ch`. The visible border/background lives on a `.input-wrap` wrapper; `.set-input` itself is transparent; the `kg`/`reps` suffix slides in on `has-val` / `:focus-within`. This deliberately replaces a CSS-grid layout that rendered inconsistently across fonts/devices — keep the JS-width approach when adding features.
- **"Haftalık Düzen" button** opens an HTML infographic modal (`.ig-*` classes) that reproduces the old poster's look but reflects the current v3 plan — there is no PNG behind it anymore.

## The backend (context, not in this repo)

`my_workout.html` is the frontend of a two-part system. The Flask API and its data live on the Oracle Cloud server, documented in [context.md](context.md):

- `app.py` at `/home/emrullah/workout-api/app.py` — two routes only: `GET`/`POST /api/workout/notes/<exercise_id>`, SQLite (`workout_notes.db`, table `notes(exercise_id TEXT PRIMARY KEY, data TEXT)`, JSON blob upserted with `ON CONFLICT DO UPDATE`).
- CORS is locked to `emrullah(xyz).github.io`. The route is exempted from YunoHost's SSOwat auth wall via an `access_by_lua_block { return }` in `/etc/nginx/conf.d/emrullah.xyz.d/workout.conf`.
- Editing frontend HTML does **not** touch the backend. If server files (`app.py`, nginx config) change, follow the git-sync protocol in the user's global rules (mirror to `oracle-infrastructure`).

## Dataset conventions

- Media filename = `{index}-{exerciseId}.{ext}` (e.g. `0025-EIeI8Vf.jpg` / `.gif`). The `id` field in JSON (`"0025"`) is the index prefix; the suffix is ExerciseDB's original media id. Thumbnail and GIF share the same basename.
- Records are ordered alphabetically by name.
- **Adding an exercise** (see how `cat-cow`/`bird dog`, ids 5202/5203, were added): drop a matching `.gif` into `videos/` and `.jpg` into `images/` using the `{id}-{suffix}` naming, insert a full 4-language record into `data/exercises.json` at its alphabetical position, and (if it's used in the plan) add the trimmed copy to `EXERCISES_RAW` in `my_workout.html`.
- Full JSON schema and body-part/equipment breakdowns are in [README.md](README.md); treat README as the outward-facing contract for the dataset.

## Deploy gotchas (GitHub Pages)

- After `git push`, publish takes 1–2 min and browsers may cache for ~10 min. After visual/design changes, suggest a `?v=N` cache-buster to the user.
- On Windows, `git push` can hang on a Windows Credential Manager prompt (especially post-reboot). If it stalls, push via token: `git push https://<user>:$(gh auth token)@github.com/<user>/<repo>.git`.
